# ADR-0023: Register cache mappings lazily from a generated index

## Status

Accepted

## Context

`nf --help` imported every cache mapping at startup. `src/pynetappfoundry/cache/__init__.py` ran `pkgutil.walk_packages` over `cache/ontap` and `cache/dii` and imported all 467 `mapping.py` modules, so each `register_mapping()` call ran as an import side effect ([ADR-0007](0007-url-tree-model-registry.md)). That pulled in about 930 `model.py` modules and cost roughly 2.3 s of the CLI's startup. A second cost sat outside the registry: `src/pynetappfoundry/clients/openapi.py` imported `jsonschema` at module level, which loads `rfc3987_syntax` and costs about 0.5 s of `import pynetappfoundry`. The measurements are in issue #903 and its PR.

## Decision

1. **Mappings register lazily from a generated, committed index.** `src/pynetappfoundry/cache/_mapping_index.py` maps each registered mapping name to its `mapping.py` module, its model class (module and qualname) and its package TOML overlay path. `ModelRegistry(index=...)` imports an indexed module on the first lookup of its name or of its model class. Only the `model_registry` singleton gets the index; a bare `ModelRegistry()` behaves as before.
2. **The index is generated by importing the real modules**, not by a text scan or a naming convention: `doit mapping_index` executes each `mapping.py` against a recording stand-in for `register_mapping`. `Cluster` registers `ClusterInfo`, so a naming convention cannot work, and a regex scan cost 57-88 ms per startup and depends on the exact text of the mapping files. `doit mapping_index --check` exits non-zero with a diff on drift and writes nothing. `doit generate_models` regenerates the index after it writes files.
3. **Package overlays apply at registration time.** `register_mapping` applies an indexed name's TOML overlay once, so the lazy registry returns the same strategies the old import-time `load_overlays` pass produced. `src/pynetappfoundry/cache/__init__.py` no longer walks packages or loads overlays. The hand-written mapping sub-packages were still imported explicitly there until #960; see [Lazy cache package exports (Issue #960)](#lazy-cache-package-exports-issue-960).
4. **A stale index degrades, it does not break.** On the singleton, a lookup miss (an unknown name, or a model class with no index entry) runs `pkgutil.walk_packages` once per process, imports only the `*.mapping` modules the index does not list (never the indexed ones, so a typo'd name costs a directory walk, not ~470 imports) and logs `mapping index is stale: <module> is not indexed; run doit mapping_index` for each. A mapping renamed inside an already-indexed file is not found by name until `doit mapping_index` runs; the drift test catches that in the repository. A missing overlay file is rediscovered once, with the same warning. Hits on indexed names never walk. `ModelRegistry.mappings` loads every indexed module, then runs the same fallback.
5. **A test compares the index with a `pkgutil` walk**, and another checks the committed file equals a fresh render, so drift fails CI.
6. **`jsonschema` is imported inside `APIWrapper.validate_body` and `validate_response`**, after their early returns, so `import pynetappfoundry` does not load it.

## Rationale

- Startup pays for the mappings a command uses instead of all 467.
- The index is exact because it is built from the real registrations, and the fallback keeps a forgotten regeneration from becoming a missing-mapping error.
- Callers keep the same registry API.

## Consequences

- Adding, renaming or removing a `mapping.py` (generated or hand-written) needs `doit mapping_index`; `doit generate_models` does it for generated ones.
- `ModelRegistry.mappings` iteration order is no longer the walk order. Every consumer sets, sorts or looks up by name.
- A stale index shows up as a one-time warning and one extra walk, not as a failure.
- ADR-0007's statement that the `__init__.py` chain registers every mapping as an import side effect no longer holds for generated mappings; an amendment there points to this ADR.
- Not changed here: index overlay paths are relative to `cache/`, so the 191 `cache/dii/**/*.toml` overlays are applied like the `ontap/` ones (#959). The `CachedClusterMetadata` and `models.ontap` import chain is deferred by #960; see [Lazy cache package exports (Issue #960)](#lazy-cache-package-exports-issue-960).

## Lazy cache package exports (Issue #960)

Decision 3's "hand-written mapping sub-packages stay imported explicitly" no longer holds. Only two of the 28 explicit `import pynetappfoundry.cache.ontap.*` lines registered a mapping on import; the rest re-exported a model, and all five hand-written mappings are in the index. The decision is:

- `src/pynetappfoundry/cache/__init__.py` imports nothing eagerly. Its exports resolve through a PEP 562 module `__getattr__` backed by a name-to-module table, so `import pynetappfoundry.cache` loads no `models.ontap` module.
- `src/pynetappfoundry/cache/_lazy.py` and `src/pynetappfoundry/cache/db.py` import `CachedClusterMetadata` inside the functions that use it.
- CLI command modules and `src/pynetappfoundry/query/job.py` import `models.ontap`, `cache.ontap.*.mapping`, `cache.refresher` and `cache.diff` inside functions, with `TYPE_CHECKING` imports for annotations. `test_cli_help_skips_ontap_models` enforces it for `nf --help`.
